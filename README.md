# 服务卷每日巡检台（纽约时间）

一个 Flask 小应用：按 `America/New_York` 当地时间每天检查一次服务卷的可用字节数，
支持网页设置巡检时刻、演练时钟，并正确处理纽约夏令时换时。

## 功能与规则

- 每日巡检一次，读取 `VOLUME_PATH`（默认 `/volume`）挂载点的可用字节数（`shutil.disk_usage`）。
- 网页可设置每日巡检时刻（HH:MM），展示当天**计划时间**与**实际可用字节数**；
  读盘失败时展示错误信息（异常类型与内容），不产生假数据。
- 夏令时：
  - **春季跳时（gap）**：不存在的当地时刻顺延到跳时后的第一个有效分钟
    （例：2026-03-08 02:30 → 实际 03:00 EDT，即 07:00Z）。
  - **秋季重复（fold）**：取第一次出现（fold=0，EDT 那次）
    （例：2026-11-01 01:30 → 05:30Z，而非 06:30Z）。
- 读盘在调度锁之外执行：**读盘期间仍可修改时刻**。
  - 已开始的巡检保留原计划时间，读盘完成后按原计划落结果；
  - 尚未开始（pending）的计划——**无论哪个纽约当地日期**——立即按新时刻重排；
    因此把演练时钟拨到别的日期改时刻、再拨回来，首页计划与后台触发都以
    最近一次保存成功的时刻为准（重启同理）。
- 同一纽约当地日期只保留一份结果（`results.local_date` 主键，`INSERT OR REPLACE`）。
- 重启后：当天已到计划时间但没有结果的巡检会补做；
  重启前已处于 `running` 的中断巡检沿用**原计划时间（及原开始时间）**重新读盘，
  即使重启后先在网页改了时刻，中断计划也不被覆盖。
- 切换纽约当地日期或重启后，首页在下次轮询前就会按最近保存成功的时刻
  生成当天计划（状态查询自带补建，不覆盖已有计划）。
- 时刻保存是**单事务原子操作**：设置与全部待执行计划一起提交，
  任一步失败整体回滚，首页提示“保存失败”，设置和待执行计划保持原值。
- 网页可**设定**演练时钟到任意 UTC 时刻，也可按秒**推进**，并可恢复真实时间；
  时钟偏移持久化在 SQLite 中。
- 故障演练钩子：设置环境变量 `FAIL_TRIGGER_PATH` 指向一个文件，文件存在时
  时刻保存接口直接报错（事务不开启写入），用于端到端验证保存失败提示；
  默认不配置则永不触发。

## 运行

### Docker Compose（交付方式）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

- 数据库存放在命名卷 `inspector-data`（容器内 `/data/inspector.db`）。
- 宿主机根目录以只读方式挂为 `/volume` 作为被巡检的“服务卷”，可按需换成真实卷。
- `READ_DELAY_SECONDS` 给读盘增加固定延迟，方便演练“读盘期间改时刻”；生产可设 0。

### 本地直接运行（无 Docker 时）

```bash
python3 -m venv .venv --without-pip   # 若系统无 ensurepip，先用 get-pip.py 引导 pip
.venv/bin/python -m pip install -r requirements.txt
DB_PATH=./data/inspector.db VOLUME_PATH=./data .venv/bin/python wsgi.py
```

## 网页入口

| 页面/接口 | 方法 | 说明 |
| --- | --- | --- |
| `/` | GET | 当天计划、当天结果、演练时钟、最近记录 |
| `/check-time` | POST | 设置每日巡检时刻（表单字段 `check_time`） |
| `/clock/set` | POST | 设定演练时钟（ISO UTC，如 `2026-03-08T13:00`） |
| `/clock/advance` | POST | 推进演练时钟（字段 `seconds`） |
| `/clock/reset` | POST | 恢复真实时间 |

## 结构

```
inspector/
  timeutil.py    # 纽约时区、HH:MM 校验、gap/fold 排程
  storage.py     # SQLite：settings / plans / results
  scheduler.py   # 后台调度线程、演练时钟、重启补做、锁外读盘
  app.py         # Flask 应用工厂与路由
  templates/index.html
tests/           # unittest：时区 5 例、调度 16 例、网页 7 例（共 28 例）
wsgi.py          # 入口
```

## 本次修复内容

问题：值班员把演练时钟拨到次日修改巡检时刻、再拨回当天后，首页仍显示旧
计划，后台也按旧时刻触发。

根因：旧实现 `set_check_time` 只重排“当前纽约日期”的当天计划，其他日期
已落库的 pending 计划保留旧 `check_time/planned_utc`；时钟拨回后这些旧
计划被原样读出。

修复：

1. `Storage.apply_check_time_change`：新时刻设置与**所有 pending 计划**的
   重排放在同一个 SQLite 事务里提交，失败整体回滚；冲突更新带
   `WHERE plans.status='pending'`，running/done/error 计划固化的时刻绝不被覆盖。
2. `Scheduler.set_check_time`：遍历全部 pending 日期按新时刻重算（含 DST
   gap/fold 处理），当天缺计划行时补建；已开始/已完成的日期跳过。
3. `Scheduler.status` / `tick`：切换纽约当地日期或重启后，缺计划行时立即按
   最近保存成功的时刻补建当天计划，首页不再依赖轮询周期才出现计划。
4. `/check-time` 路由捕获存储异常并提示“保存失败…保持原值”，失败时不唤醒
   调度线程，设置与待执行计划维持原值。
5. 重启恢复语义不变并补齐验证：running 中断计划即使在重启后先改时刻，
   仍沿用原计划时间与原开始时间补做。

## 已验证的演练场景（真实 HTTP 端到端）

1. **跨日改时刻（本次缺陷场景）**：时钟拨到次日把 09:00 改为 11:00，再拨回
   当天，首页与后台均按 11:00（15:00Z）执行；旧时刻 13:00Z 不再触发，
   新时刻触发后同日仅一份结果。
2. 换时：春季 02:30 顺延至 03:00 EDT（07:00Z）执行；秋季 01:30 取第一次 05:30Z 执行。
3. 读盘期间改时刻：读盘窗口内把 09:00 改为 11:00，进行中的计划与结果仍记
   09:00，设置本身更新为 11:00，未开始的计划按 11:00 排。
4. 重启补做：
   - 读盘中杀进程，计划停在 `running` 且无结果，重启后**先改时刻再补做**，
     仍沿用原计划/原开始时间成功；
   - 手工构造到期 `pending` 无结果计划，重启后自动补做，计划时间不变；
   - 当天已有结果时重启不重复读盘。
5. 保存失败：通过 `FAIL_TRIGGER_PATH` 注入写失败，首页提示保存失败，
   设置与待执行计划（时刻、计划绝对时间、状态）全部保持原值。
6. 读盘失败：挂载点不存在时网页显示错误徽标与异常文本，同日只记一份，计划状态 `error`。
